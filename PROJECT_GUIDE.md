# Project Guide: Django Sites with Reusable Pages and Design Demos

This guide describes both the current VITA menu website and a practical way to
reuse its approach for another site. The future-project guidance is deliberately
flexible: another site may have different pages, components, content, visual
style, or backend needs.

## 1. Project purpose and current status

This repository contains a Persian, right-to-left menu website for VITA, a juice
and ice-cream shop. The production page and experimental designs live in the
same Django project:

- `/` is the main page and uses the default page composition.
- `/demos/` is a gallery of saved design explorations.
- `/demos/demo-01/` is the Orange Fresh design. It uses a custom Hero, Demo-01
  styling, and supplied fruit imagery; the other page components remain the
  defaults.
- `/demos/hero-fresh/` is a legacy URL alias for Demo 01.

The intent is to experiment without silently replacing the main page. A chosen
demo can be promoted to `/` as a deliberate change.

## 2. Current technology

- **Backend:** Django 5.x, Python 3.12, Gunicorn.
- **Templates:** Django templates, including reusable template partials.
- **Frontend:** HTML, CSS, and JavaScript; there is no frontend build system.
- **Static files:** Django static files, collected for deployment and served by
  WhiteNoise.
- **Database configuration:** SQLite in a Docker named volume.
- **Menu content today:** Defined in `menu/views.py` as the `MENU_DATA` Python
  constant; it is not currently loaded from SQLite or editable through Django
  Admin.
- **QR code:** Generated by the Django view at `/qr/` using `qrcode`.
- **Development and deployment:** Docker Compose, with a GitHub Actions SSH
  deployment workflow for the `third-idea` branch.

## 4. How a request becomes a page

For the main page, the flow is:

1. `restaurant/urls.py` maps `/` to `menu.views.menu`.
2. The view calls `render_composition()` in `menu/views.py`.
3. `render_composition()` prepares menu groups and the component-template map.
4. `templates/layouts/menu_page.html` includes the selected header, Hero, menu,
   visit/QR, and footer templates.
5. The browser receives the rendered HTML and loads the shared stylesheet and
   JavaScript, plus any optional demo-specific assets.

The current default component map is `DEFAULT_COMPONENTS` in `menu/views.py`:

| Slot | Default template |
| --- | --- |
| Header | `components/header/default.html` |
| Hero | `components/hero/default.html` |
| Menu | `components/menu/default.html` |
| Visit / QR | `components/visit/default.html` |
| Footer | `components/footer/default.html` |

Demo 01 passes a different Hero template to `render_composition()` and adds
page metadata, a page class, and its own CSS/JavaScript paths. Its styles are
scoped under `.hero-demo-page`, which keeps its design from restyling `/`.

The five component names are specific to this menu page, not a required list for
future projects. A new site should choose component slots that fit its content.

## 5. Available local routes

The current local `.env` configures `HOST_PORT=8002`; if that changes, replace
`8002` below with the configured port.

| URL | Purpose |
| --- | --- |
| `http://127.0.0.1:8002/` | Default VITA menu page |
| `http://127.0.0.1:8002/demos/` | Design-demo gallery |
| `http://127.0.0.1:8002/demos/demo-01/` | Demo 01: Orange Fresh |
| `http://127.0.0.1:8002/demos/hero-fresh/` | Legacy alias for Demo 01 |
| `http://127.0.0.1:8002/qr/` | Generated QR PNG for the root page |

The deployment's public hostname is configured outside the repository. The
public URL therefore cannot be determined from the source tree alone.

## 6. Local development with Docker

Docker is the recommended way to run the project consistently. The Compose
service builds the image, reads `.env`, binds the app to `127.0.0.1:${HOST_PORT}`
on the host, persists SQLite data in a named volume, collects static files, and
starts Gunicorn on port 8000 inside the container.

First-time setup:

```sh
cp .env.example .env
# Edit .env: set a private DJANGO_SECRET_KEY and choose HOST_PORT/SQLITE_VOLUME.
docker compose up --build
```

Useful commands:

```sh
# Build and run in the background
docker compose up -d --build

# Run the Django test suite
docker compose run --rm web python manage.py test

# Run Django's general configuration checks
docker compose exec -T web python manage.py check

# See container state and logs
docker compose ps
docker compose logs -f web

# Stop the service; the named data volume remains
docker compose down
```

`Dockerfile` starts from `python:3.12-slim`, installs `requirements.txt`, copies
the project into `/app`, and starts Gunicorn. `docker-compose.yml` supplies the
environment and persistent paths. The Compose port is bound to loopback so an
external reverse proxy can provide public HTTP/HTTPS access.

For two local checkouts running at once, use different `HOST_PORT` and
`SQLITE_VOLUME` values in each checkout.

## 7. Backend structure and how it can grow

The current backend is intentionally small:

- `restaurant/settings.py` loads the secret key, host allowlist, database path,
  static settings, and HTTPS/proxy security options from environment variables.
- `restaurant/urls.py` maps named URL patterns to views.
- `menu/views.py` prepares menu context, selects page compositions, renders the
  gallery, and generates the QR response.
- `menu/tests.py` checks the root and demo compositions, product rendering, and
  QR endpoint.
- `restaurant/wsgi.py` exposes Django's WSGI application to Gunicorn.

There are currently no Django models or migrations for menu items. `MENU_DATA`
is the content source. For a small, mostly static site this is simple; if staff
need to edit products, prices, availability, or categories without code
changes, a future version could add Django models, migrations, and an admin
workflow. That is a product decision, not a requirement for component-based
pages.

Other backend features can be added as the site needs them: contact/order forms,
authentication, APIs, analytics, or additional data models. Each should have an
explicit route, view/service responsibility, configuration, and tests rather
than being mixed into template composition logic.

## 8. How to add a design demo

For another visual direction of the same page:

1. Decide which existing page slots should change and which can stay default.
2. Add a named template variant only for each component whose structure or
   behavior differs. For a color-only direction, prefer theme variables and
   scoped styles rather than duplicating unchanged HTML.
3. Put the demo's CSS, JavaScript, and images in a named directory such as
   `menu/static/menu/demos/demo-02/`.
4. Add a view composition in `menu/views.py`, selecting the variants and
   passing page-specific metadata/assets.
5. Add a named route in `restaurant/urls.py` and a card in
   `templates/demos/index.html`.
6. Add or extend tests to ensure the route renders and the root page remains
   isolated from demo-only assets.
7. Check mobile and desktop layouts, run tests and Django checks, then keep the
   demo available for comparison.

The layout can select any combination of the existing component slots. A new
variant for all five does not require a new layout. If the concept adds a new
kind of section, extend the layout with a deliberate slot or create a suitable
layout for that page type.

## 9. How to add a different kind of page

Do not force every future page into `menu_page.html`. First decide whether it
shares the menu page's structure:

- **Same page purpose and structure:** reuse its layout and choose default or
  alternate component variants.
- **Different page type, some shared parts:** create a new layout under
  `templates/layouts/` and include reusable pieces where they fit.
- **Separate product/brand or independent lifecycle:** consider a separate
  Django app or repository. A different visual experiment for the same brand
  usually belongs in this project as a demo.

Examples of new page types could include an About page, campaign landing page,
contact page, or a product detail page. Their component vocabulary should follow
their content (for example, story, testimonial, gallery, contact form), rather
than being limited to Header/Hero/Menu/Visit/Footer.

## 10. CSS and design-system guidance

The templates have been split into components, but most existing production
styles are still together in `menu/static/menu/menu.css`. Demo 01 adds a separate
stylesheet with `.hero-demo-page` scoping. This is the current state—not a
requirement for future sites—and broad selectors in the shared stylesheet can
still influence multiple page compositions.

If the project gains many pages or design variants, evolve the CSS gradually:

- Keep reset, typography, and shared tokens in a small base stylesheet.
- Put component styles near their component or in clearly named files such as
  `header.css`, `hero.css`, and `menu.css`.
- Put page-theme overrides in page-specific files or use explicit theme classes
  and CSS custom properties.
- Avoid copying a whole component only to change colors, spacing, or type scale.
- Continue respecting responsive layouts, keyboard/focus states, and
  `prefers-reduced-motion`.

The project currently has a reusable component structure and a demo gallery; it
is an early component system, not yet a fully documented design system. A design
system typically also defines shared tokens, usage rules, accessibility
expectations, and documented component states.

## 11. Git workflow

Git tracks code history and provides a safe way to compare, preserve, and deploy
design directions. This repository currently uses the `third-idea` branch for
this version of the menu. The deployment workflow is configured to run after a
push to that branch.

Typical feature workflow:

```sh
git status --short
git switch -c feature/short-description
# Make and test a focused change.
git diff --check
git diff
git add path/to/intended-file
git commit -m "Describe the change"
git push -u origin feature/short-description
```

For a small requested change directly on the current branch, check the branch
and status first, stage only the intended files, review the staged diff, then
commit and push. Do not include `.env`, generated output, or unrelated local
work. A commit is a saved local change; a push sends commits to the configured
Git remote. A push to `third-idea` can also initiate deployment.

Useful inspection commands:

```sh
git status --short --branch
git log --oneline --decorate -10
git diff
git diff --cached
```

## 12. Deployment workflow

The `third-idea` push workflow in `.github/workflows/deploy.yml` connects to the
configured server over SSH. On the server it fetches the branch, builds the
container, runs tests, restarts Compose, runs Django's deployment checks, and
prints container status.

The server needs Docker, Docker Compose, Git, a checkout of the repository, a
production `.env`, and an HTTPS-terminating reverse proxy. The GitHub Actions
Environment named `third-idea` must contain deployment secrets (`SERVER_HOST`,
`SERVER_USER`, `SERVER_SSH_KEY`, and `DEPLOY_PATH`; `SERVER_PORT` is optional).
Secret values must not be copied into documentation or committed files.

For deployment, configure `DJANGO_ALLOWED_HOSTS` for the real hostname and
enable the HTTPS/proxy-related settings described in `README.md`. The public
website hostname depends on server and DNS configuration and is not specified
in this repository.

## 13. Terms used in this project

- **Component / template partial:** a reusable piece of a rendered page.
- **Variant:** an alternate implementation of a component, such as a distinct
  Hero design.
- **Composition:** the selection of variants assembled into one page.
- **Demo gallery:** a page for navigating saved design compositions.
- **Component-driven design exploration:** creating and comparing compositions
  while keeping the main page stable.
- **Design system:** a broader set of reusable components, tokens, documented
  rules, and accessibility guidance. This project can grow toward one, but its
  current setup is smaller and simpler.

## 14. Starter checklist for another project

1. Define the site's pages and the content each page must present.
2. Choose a backend based on data and behavior needs; use Django when its
   routing, templates, forms, models, or admin are useful.
3. Split each page into meaningful, reusable sections—not an arbitrary fixed
   number of components.
4. Create a shared layout for each genuinely shared page structure.
5. Establish base styles/tokens, then isolate component and page-theme styles.
6. Add named routes and tests for the main page and important compositions.
7. Run locally in Docker, keep secrets in ignored environment files, and commit
   only intentional source changes.
8. Add deployment automation only after the server, domain, reverse proxy, and
   secret handling are configured.
